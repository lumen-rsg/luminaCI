Architecture
A pipeline you can
actually trust.

Lumina CI is a set of small .NET services fronted by a YARP gateway that owns auth and fans requests out to the workers. Sources are fetched, built in isolated containers, signed, scanned, and published — every stage is an independently deployable service.

Isolated Builds

Every rpmbuild runs in a throwaway container on a dedicated network — cap-dropped, memory-capped, non-root. Untrusted .spec files stay in the sandbox.

PGP-Signed Artifacts

security-service signs every published RPM with a managed GPG key. Detached signatures are stored alongside the artifacts they cover.

CVE Scanning

scanner-service runs Trivy against each artifact and records findings per-artifact. Vulnerabilities surface before publish, not after.

Managed Repository

repository-service maintains repo metadata and publishes packages to an HTTP-served repo. createrepo-style updates land on every publish.

Git / Tar / rsync

Pull sources from a Git repo, a tarball URL, or rsync. Declare them in conf.ini or manage them live from the console — whichever fits your flow.

Secure by Default

HttpOnly cookies, rotated refresh tokens, per-IP rate limiting, exponential lockout, at-rest encryption of pipeline secrets. No default credentials.

conf.ini — declare a source package 
[package]
name="aurora"
source="https://github.com/lumen-rsg/aurora.net"
source_type="git"
source_branch="main"
build_image="lumina-dotnet-build:latest"
Build Security
Untrusted .spec files,
sandboxed by design.

A build container runs dnf builddep and rpmbuild over untrusted .spec files — effectively arbitrary shell as root inside the container. Several layers turn that from a host-escape primitive into a constrained sandbox.

No Socket Mount

build-service never mounts /var/run/docker.sock. It reaches the daemon through docker-socket-proxy, which whitelists only the endpoints it needs.

Isolated buildnet

Build containers attach to lumina-buildnet — separate from lumina-network. Outbound internet for dnf/git, but no path to Postgres, RabbitMQ, MinIO, or Trivy.

Container Caps

cap-drop=ALL plus the minimum rpmbuild needs, pids-limit, memory==swap, CPU quota, no-new-privileges, --init. Tunable via BUILD_* env vars.

Non-root Images

rpm-build and dotnet-build images create a rpmbuilder user (uid 1000) and run rpmbuild as it. No sudo in the images.

Isolation Layers
Four walls around every build.
docker-socket-proxy filtered
The host socket is mounted here, but this container only forwards explicitly enabled endpoints to build-service. A compromised builder cannot docker run arbitrary images or read the host filesystem.
whitelisted Docker API
CONTAINERS: 1   # create/start/logs/wait/stop/remove
IMAGES:     1   # list + pull
POST:       1
EXEC:       0   # denied
NETWORKS:   0   # denied
VOLUMES:    0   # denied
BUILD:      0   # denied
lumina-buildnet isolated
A dedicated bridge network for build containers, intentionally separate from lumina-network. Builders get outbound internet but cannot reach any stateful service.
network split
networks:
  lumina-network:        # app + infra
    driver: bridge
  lumina-buildnet:       # untrusted builders
    driver: bridge
# build containers attach ONLY to buildnet —
# no route to postgres / rabbitmq / minio / trivy
resource limits hardened
Each build container is capped on memory, PIDs, CPU, and capabilities — and denied privilege escalation. Fork bombs and OOM can’t reach the host.
per-build caps
--cap-drop=ALL
--memory=2147483648
--memory-swap=2147483648   # no overcommit
--pids-limit=512
--cpu-quota=150000        # 1.5 CPUs
--security-opt=no-new-privileges
--init
userns-remap remapped
For production, enable user-namespace remapping at the daemon. Container root maps to an unprivileged host uid, so even a sandbox escape lands on uid 100000+, not host root.
/etc/docker/daemon.json
{
  "userns-remap": "dockremap"
}
# container root → host uid 100000+
# the compose stack keeps working unchanged
Controls
Every control, named and enforced.

Beyond the build sandbox, the rest of the stack is hardened end to end. Each control below is wired into the compose file or service code — not a roadmap item.

CodeControlWhat it enforces
SEC-01Sealed infraPostgres / Redis / RabbitMQ / MinIO / Trivy are never published to the host — internal-only on lumina-network
SEC-04Re-validated JWTEvery downstream service independently re-validates the bearer token — defense in depth, not trust-by-network
SEC-05Cookie sessionShort-lived access JWT in an HttpOnly, Secure, SameSite=Strict cookie; rotated refresh tokens in Redis
SEC-012Rate-limitedPer-IP global token bucket plus a strict per-IP+username login bucket; exponential account lockout
SEC-013Secrets at restPipeline secrets (WebhookSecret, GitToken) encrypted with AES-256-GCM before they touch the DB
SEC-015Body capsPer-route request-body limits — oversized uploads rejected at the door except on the two genuine upload routes
SEC-020TLS everywherenginx terminates TLS for the console; :80 only redirects to :443; no app traffic in the clear
SEC-024Fail closedFatal errors propagate a non-zero exit so Docker’s restart policy can tell a crash from a clean stop

API
One gateway.
Every route authenticated.

All routes are exposed through the gateway at /api/*. Browser sessions authenticate via an HttpOnly cookie automatically; API clients reuse the cookie jar or send a bearer token.

authenticate
curl -kc cookies.txt -X POST \
  https://localhost/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"…"}'

# sets HttpOnly lumina_access + lumina_refresh
use the API
# list builds
curl -kb cookies.txt \
  https://localhost/api/builds?page=1 \
  | jq '.data.builds[] | {id, status}'

# trigger a pipeline
curl -kb cookies.txt -X POST \
  https://localhost/api/pipelines/{id}/trigger
Session model — cookie vs. bearer

Browsers get a hardened cookie session; automation gets the same JWT as a bearer header. The raw token is never returned to client-side JS, so XSS can’t read it.
